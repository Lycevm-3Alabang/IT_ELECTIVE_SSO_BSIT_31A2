# IT-ELECTIVE - SSO Integration Documentation

## Overview

This project provides a Single Sign-On (SSO) system that allows client applications to authenticate users through a central authentication service instead of implementing separate login systems.

The SSO system is built with ASP.NET Core. The Gateway handles the central authentication process, while client applications use the Gateway to authenticate users and establish their own local sessions.

This documentation provides setup instructions, architecture details, JWT claim references, integration guides, working code examples, error documentation, and frequently asked questions to help developers integrate their applications with the SSO system.

## SSO Configuration

The current SSO Gateway and configured callback URL are:

* **SSO Base URL:** `https://localhost:7425`
* **Callback URL:** `https://localhost:7300/callback.html`

The callback URL is intended for the client application that uses the `callback.html` handler. Other client applications must use their own callback URLs when their integration requires separate handlers.

### ASP.NET Core Configuration

Configure the SSO settings in the client application's `appsettings.json`:

```json
{
  "Sso": {
    "BaseUrl": "https://localhost:7425",
    "CallbackUrl": "https://localhost:7300/callback.html"
  }
}
```

Read the settings in C# using:

```csharp
var ssoBaseUrl = configuration["Sso:BaseUrl"];
var callbackUrl = configuration["Sso:CallbackUrl"];
```

Make sure the Gateway is running at the configured address and that the callback URL is registered and supported by the Gateway.

### Node.js Configuration

For Node.js/Express integrations, configure the environment variables in `.env`:

```env
SSO_BASE_URL=https://localhost:7425
CALLBACK_URL=https://localhost:7300/callback.html
```

Keep secrets in environment variables or a secure configuration provider. Do not commit actual signing keys, passwords, or session secrets to the repository.

## Authentication Overview

The typical authentication process follows these steps:

1. The user opens a client application.
2. The client checks whether the user has an active authenticated session.
3. If authentication is required, the client redirects the user to the SSO Gateway.
4. The user authenticates through the Gateway.
5. The Gateway returns the authentication result to the registered callback URL.
6. The client validates the authentication result.
7. The client establishes a local session and uses the verified user information to protect its pages.

The exact endpoint names, callback parameters, and token format depend on the implementation configured in the Gateway.

## JWT Claims and Validation

If the Gateway returns a JSON Web Token (JWT), the client must validate the token before trusting its claims.

The validation process should include:

1. Verify the token signature using the Gateway's trusted signing configuration.
2. Validate the expiration time.
3. Validate the issuer and audience when required.
4. Confirm that the required user claims are present.
5. Use the verified claims to identify the user and apply authorization rules.

Decoding a JWT only reveals its contents; it does not prove that the token is authentic.

Common user claims may include:

| Claim        | Description                                     |
| ------------ | ----------------------------------------------- |
| `sub`        | User identifier                                 |
| `email`      | User's email address                            |
| `groups`     | Group memberships                               |
| `levels`     | Application-specific user levels or permissions |
| `tenant_app` | Application or tenant information, if supplied  |

The actual claim names and data types must match the token generated by the Gateway.

For further details, see `jwt-claims.md`.

## Security Recommendations

* Always validate authentication results before creating a user session.
* Never trust a JWT simply because it can be decoded.
* Keep signing keys and credentials out of source control.
* Use HTTPS for authentication and callback traffic.
* Validate callback destinations against approved client URLs.
* Use state validation or an equivalent CSRF protection mechanism where supported by the authentication flow.
* Protect session cookies with appropriate security settings.
* Require authentication for protected application pages.
* Avoid recording passwords, signing keys, live JWTs, or session cookies in logs.
* Test expired tokens, invalid tokens, unauthorized access, and logout behavior.

## Development and Testing

Before testing a client integration:

1. Start the Gateway project.
2. Confirm that the Gateway is accessible at `https://localhost:7425`.
3. Check that the client callback URL is configured correctly.
4. Start the client application.
5. Test login with valid credentials.
6. Verify that the callback completes successfully.
7. Confirm that protected pages require authentication.
8. Check that user claims are read correctly.
9. Test logout and invalid or expired authentication results.
10. Review application logs and browser console errors when troubleshooting.

Because this project uses local HTTPS endpoints, ensure the development certificates are trusted by your browser and client applications.
