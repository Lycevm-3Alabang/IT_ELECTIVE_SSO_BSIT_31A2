# JWT Claims Reference

## Overview

A JSON Web Token (JWT) is a compact token format that can carry information about an authenticated user. This document describes common JWT fields and how a client should validate them.

The actual claims depend on the token generated by the Gateway. Confirm the claim names by inspecting the token-generation code in the project.

## JWT Structure

A JWT normally contains three parts separated by periods:

1. Header — identifies the token type and signing algorithm.
2. Payload — contains claims about the user and token.
3. Signature — allows the receiver to verify token integrity.

The payload is encoded, not encrypted by default. Do not store passwords, signing keys, or other secrets in JWT claims.

## Common Claims

| Claim    | Purpose                                                       |
| -------- | ------------------------------------------------------------- |
| `sub`    | Identifies the subject or user.                               |
| `iss`    | Identifies the token issuer.                                  |
| `aud`    | Identifies the intended recipient.                            |
| `exp`    | Specifies when the token expires.                             |
| `iat`    | Indicates when the token was issued.                          |
| `email`  | May contain the user's email address.                         |
| `name`   | May contain the user's display name.                          |
| `groups` | May contain group memberships, if supported.                  |
| `level`  | May contain an application-specific user level, if supported. |

The Gateway may use different claim names or omit some of these claims.

## Example Payload

The following is an illustrative payload, not a confirmed token from the project:

```json
{
  "sub": "user-123",
  "iss": "https://localhost:7001",
  "aud": "example-client",
  "email": "user@example.com",
  "name": "Example User",
  "groups": ["Users"],
  "level": "Standard",
  "iat": 1791504000,
  "exp": 1791507600
}
```

Use the real issuer, audience, claim names, and expiration settings from the Gateway implementation.

## JWT Validation Steps

1. Obtain the token using the authentication flow supported by the Gateway.
2. Validate the signature using the correct trusted signing key or public key.
3. Validate the issuer (`iss`) against the expected issuer.
4. Validate the audience (`aud`) against the intended client.
5. Validate the expiration (`exp`) and other applicable time claims.
6. Confirm that required claims are present.
7. Use the verified claims to establish the user's identity and authorization context.

Do not accept a token merely because its payload can be decoded.

## Accessing User Information

After successful validation, applications may read the claims they need.

Examples include:

* Email for displaying or identifying the authenticated user.
* Groups for group-based access control.
* Level for application-specific access rules.

Check that these claims exist and have the expected data types before using them.

## Security Recommendations

* Use a trusted JWT validation library.
* Never trust unverified payload data.
* Do not disable signature, issuer, audience, or expiration validation to make authentication work.
* Protect tokens from being exposed in URLs, logs, and browser storage.
* Follow the actual token format and validation requirements of the Gateway.
